# 项目管理规范

本文档记录 CPA 课程归档项目的项目管理规范，包括任务管理方式、测试驱动原则、缺陷分类、缺陷管理流程和测试计划模板。

## 0. 任务管理方式约定

> **重要约定**：本项目只维护**一个**任务状态来源，避免多套不同步。

### 唯一任务状态来源

**`docs/project-management/TASK_STATUS.md`**（Markdown 文档）

- 所有任务状态、进度、详情以本文档为准
- AI 助手直接编辑本文档更新任务状态
- Git 版本控制，可追溯历史
- 在 GitHub 仓库中，随时可查

### 飞书 Base（模板保留，不日常维护）

- **链接**：https://zcnjheoajxng.feishu.cn/base/OYubbekdXarUIHsJenRcg7nsnFc
- **用途**：保留作为可视化模板，供其他同事参考（飞书表格形式更一目了然）
- **不日常更新**：避免双轨维护导致不同步
- **字段设计**：任务名称 | 父任务 | 状态 | 负责人 | 优先级 | 预计时间 | 实际时间 | 备注

### 任务状态更新规则

1. 每次任务状态变化时，AI 助手必须同步更新 `TASK_STATUS.md`
2. 大任务完成后，在 `TASK_STATUS.md` 中记录完成时间和结果
3. 发现新任务时，添加到 `TASK_STATUS.md` 对应位置
4. 任务有层级关系时，用缩进或编号表示（如 2.1、2.1.1）

### 模板同步规则

> **重要**：TASK_STATUS.md 的结构发生变化时，必须同步更新飞书 Base 模板，保持两者结构一致。

**触发同步的场景**：
- 新增/删除任务字段（如新增"阻塞原因"字段）
- 调整任务分类/层级结构
- 修改状态标记定义
- 新增任务类型（如"测试任务"、"维护任务"）

**同步操作**：
1. 更新 `TASK_STATUS.md` 的结构
2. 打开飞书 Base（链接见上），同步调整字段、视图、分组
3. 在本文档中记录模板更新时间和变更内容

**当前模板字段**（最后同步：2026-08-27）：

| 字段 | 类型 | 说明 |
|------|------|------|
| 任务编号 | 文本 | 如 1.1、2.1.1，用编号建立层级关系 |

### 状态标记

- ✅ 完成

## 1. 测试驱动原则

### 1.1 单样本测试优先

- 每个新功能/新流程先做**单样本测试**，验证通过后再批量执行
- 测试前明确**测试目标、范围、步骤、通过标准**，记录到 `docs/TEST_PLAN_*.md`
- 测试过程中发现的问题立即记录，分类处理

### 1.2 测试通过标准

每个测试任务必须明确通过标准，例如：
- 视频下载：文件完整、时长正确、可播放
- 视频压缩：时长误差<2秒、编码格式正确、可播放
- 音频转文字：转写字数合理、专业术语识别准确
- 知识库生成：知识点完整、结构清晰、可检索

## 2. 缺陷分类与处理原则

基于成熟的软件缺陷管理方法论，问题按**严重程度**和**优先级**分类。

### 2.1 严重程度（Severity）

| 严重程度 | 定义 | 示例 |
|----------|------|------|
| 致命（Blocker） | 核心流程完全不可用、数据丢失 | 转写结果全部丢失、视频文件损坏 |
| 严重（Critical） | 主要功能受损，影响关键流程 | 批量脚本bug导致部分结果丢失 |
| 一般（Major） | 次要功能异常，不影响核心流程 | 上传路径缺少一层目录、OCR个别错字 |
| 轻微（Minor） | 界面/文案/路径错误，改进类建议 | 文档错别字、日志格式不统一 |

### 2.2 优先级（Priority）

| 优先级 | 定义 | 处理时机 |
|--------|------|----------|
| 高（High） | 影响核心业务，必须尽快修复 | 当前迭代立即处理 |
| 中（Medium） | 影响部分功能，可正常使用 | 下个迭代处理 |
| 低（Low） | 不影响功能，体验优化类 | 顺手修复或积压处理 |

### 2.3 处理原则

- **小问题顺手修复**：一般/轻微 + 低/中优先级，测试过程中直接修复，不阻塞测试进度
- **大问题讨论处理**：致命/严重 + 高优先级，记录到测试计划，测试完成后讨论处理
- 所有问题必须记录，包括：问题描述、影响范围、分类、处理状态、解决方案

### 2.4 分类决策矩阵

|  | 高优先级 | 中优先级 | 低优先级 |
|--|----------|----------|----------|
| 致命 | 立即停止，讨论解决 | 记录，尽快讨论 | 记录，讨论 |
| 严重 | 记录，讨论处理 | 记录，下个迭代 | 顺手修复 |
| 一般 | 顺手修复 | 顺手修复 | 顺手修复 |
| 轻微 | 顺手修复 | 顺手修复 | 积压处理 |

## 3. 缺陷管理流程

```
发现 → 分类（严重程度+优先级） → 记录 → 处理（顺手修复/讨论处理） → 验证 → 关闭 → 报告
```

### 3.1 发现

- 测试过程中、批量执行过程中、用户反馈中发现问题
- 立即记录问题描述和复现步骤

### 3.2 分类

- 按严重程度和优先级矩阵分类
- 确定是小问题（顺手修复）还是大问题（讨论处理）

### 3.3 记录

- 小问题：记录到测试计划文档的"小问题"表格
- 大问题：记录到测试计划文档的"大问题"表格，标注"待讨论"
- 记录内容：问题描述、影响范围、分类、发现时间、处理状态

### 3.4 处理

- 小问题：测试过程中直接修复，记录解决方案
- 大问题：测试完成后与用户讨论，确定解决方案和处理时机

### 3.5 验证

- 修复后必须验证问题已解决
- 验证方式：重新执行相关步骤、检查输出结果

### 3.6 关闭

- 验证通过后关闭问题
- 记录关闭时间和验证结果

### 3.7 报告

- 每个测试任务完成后，在测试结果记录中汇总问题处理情况
- 批量任务完成后，在任务报告中汇总缺陷统计

## 4. 测试计划文档模板

每个测试任务创建 `docs/TEST_PLAN_*.md`，包含以下章节：

```markdown
# 测试计划：[测试名称]

## 测试目标

[明确测试要验证什么]

## 测试范围

[明确测试包含什么，不包含什么]

## 测试步骤与状态

| 序号 | 步骤 | 状态 | 说明 |
|------|------|------|------|
| 1 | [步骤1] | ✅/❌/⏳ | [说明] |
| ... | ... | ... | ... |

## 发现的问题

### 小问题（顺手修复）

| 问题 | 影响 | 修复方案 | 状态 |
|------|------|----------|------|
| ... | ... | ... | ... |

### 大问题（讨论处理）

| 问题 | 影响 | 处理建议 | 状态 |
|------|------|----------|------|
| ... | ... | ... | ... |

## 测试通过标准

[明确测试通过的条件]

## 测试结果记录

- 测试完成时间：
- [关键指标1]：
- [关键指标2]：
- 遗留问题：
```

## 5. 任务报告规范

每次批量任务完成后生成报告，记录到飞书：

- 处理了哪些讲座/课程
- 视频/文档下载状态和文件大小
- 压缩参数和最终体积
- 遇到的问题和解决方案
- 知识库更新情况
- 做题结果
- 缺陷统计（按严重程度和优先级分类）

报告模板：`reports/REPORT_TEMPLATE.md`
