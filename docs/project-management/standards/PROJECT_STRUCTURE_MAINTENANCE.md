# 项目结构维护规范

> **文档类型**：Governance（治理规范）
> **更新频率**：维护规则变更时
> **维护者**：AI自动维护
> **读者**：AI代理（项目维护时必须遵守）

本文档记录项目结构维护的详细规则，包括结构维护原则、文件归属原则、网盘上传内容筛选、测试闭环检查、状态查询协议触发机制，以及批量重命名与结构整改流程（SOP，第六章）。

> **文档职责边界**：
> - 本文档：项目结构维护相关规则
> - `DOCUMENTATION_GUIDE.md`：文档写作指南（组织、分解、分类、Docs as Code、定期梳理、AI友好写作）
> - `DOCUMENTATION_OPTIMIZATION.md`：文档优化流程和变更驱动流程

> 本文档是从原 `PROJECT_MAINTENANCE.md` 第一至五章拆分而来。

## 一、结构维护原则

1. **GitHub 仓库只放代码和文档**：Skill 脚本、项目文档、工作流、报告模板、加密凭证。生成结果（视频、PDF、文字稿、音频）不放在项目目录，放本地 `~/Desktop/高顿/` 和百度网盘。
2. **脚本统一放 `scripts/`**：所有可执行脚本（Python、Shell）统一放在 `scripts/` 目录，不分散在各子目录。
3. **文档按专业领域分类**：`docs/project-management/`（项目管理）、`docs/development/`（开发文档），WORKFLOW.md 只保留总体流程和索引。
4. **任务文档不放根目录**：任务状态、测试计划、项目计划等统一放 `docs/project-management/`。
5. **定期清理**：测试文件、临时日志、残留目录及时清理，不堆积。
6. **.gitignore 检查（文件和目录变化时强制）**：当项目结构发生变化（新增目录、移动文件、删除文件、新增文件类型）时，必须检查 .gitignore 是否需要更新，确保新的文件类型或目录被正确忽略；提交前运行 `git status` 确认没有不该提交的文件（视频、PDF、音频、密钥明文、临时文件等）；发现新的临时文件类型或大文件类型时及时补充到 .gitignore。

### 1.1 检查触发时机

- 开始新任务前：读取项目文档时检查结构
- 完成大任务后：检查是否产生新的散乱文件
- 发现结构问题时：主动梳理调整，不等待积累
- **文件和目录有变化时**：新增/移动/删除文件或目录后，必须检查 .gitignore 是否需要更新
- **新增文件类型时**：遇到之前没有的文件类型（如 .env、.zip、node_modules/），必须检查是否需要添加到 .gitignore

### 1.2 文件去留与沉淀判据

> 用于判断一份**存量**文档该「保留 / 归档 / 沉淀为模板或规范 / 删除」。第一判据是它对后续工作的价值，而不是"写都写了"的沉没成本，也不是篇幅长短。

1. **去留第一判据＝对后续工作是否为必要输入**：能明确指出未来哪个环节会读它、以它为操作依据 → 保留；找不到任何具体使用场景、只是"也许以后有用" → 归档。归档用 `git rm`，文件仍可通过 `git log` / `git show` 永久取回，不占工作区也不怕丢，因此不必为"以防万一"而堆积。
2. **按性质分流，不一删了之**：
   - 一次性过程数据（任务报告、测试计划、整改清单、验证过程稿等）→ 归档；
   - 其中**可复用的结构**先抽成 `templates/` 模板，再归档一次性原件；
   - 稳定、可复用的方法与规则 → 沉淀进对应规范，而不是留在某份过程稿里。
3. **SSOT 去重**：若一份文档的职责已被某个权威源全面承接，删除原件并**级联清理所有引用**，不在两处重复维护（例：PROJECT_PLAN 被 REQUIREMENTS / WORKFLOW / BATCH_TASK_EXECUTION / active 台账承接后删除）。
4. **历史轨迹不改写**：ADR、CHANGELOG、"已解决问题"记录保留当时事实与被否方案，不因后续改名或方案被推翻而回改；它们的价值是可追溯，而不是指导当前操作。
5. **判不准就高不就低**：拿不定留删时，先列「保留 / 归档 / 沉淀」清单及依据，按 AGENTS.md 的 L1 高扩散变更门禁（先出全量清单、用户确认后执行）处理，不擅自删除。

## 二、文件归属原则

| 文件类型 | 放置位置 | 说明 |
|----------|----------|------|
| 通用规范/流程 | `docs/` 对应子目录 | 如 QUALITY_ASSURANCE.md、PROJECT_MAINTENANCE.md |
| 通用模板 | `project-management/task-reports/` 或 `docs/` | 如 REPORT_TEMPLATE.md、VERIFICATION_TEMPLATE.md |
| 具体课程产出物 | 对应课程目录下 | 如 video.mp4、知识拆解.md、考试指导.md、transcript.md |
| 具体课程验证报告 | 对应课程目录下 | 如 VERIFICATION.md（综合报告）或 验证报告_<对象>_<范围>.md（专项报告） |
| 具体课程测试计划 | `docs/project-management/` | 测试计划是项目管理文档，不是课程产出物 |
| 具体任务报告 | `project-management/task-reports/` 或对应课程目录 | 根据报告性质决定 |

**原则**：针对具体课程/讲座的产出物，放在对应课程目录下；通用模板和规范放在 `docs/` 或 `project-management/task-reports/` 下。

## 三、网盘上传内容筛选原则

百度网盘只上传**面向使用者**的内容，技术过程文档不上传。

### 3.1 上传分类

| 类别 | 上传？ | 示例 | 说明 |
|------|--------|------|------|
| **视频** | ✅ 上传 | video.mp4 | 课程视频 |
| **知识文档** | ✅ 上传 | 知识拆解.md, 考试指导.md | 知识本身和考试指导 |
| **讲义原件** | ✅ 上传 | docs/*.pdf | 原始讲义 |
| **讲义文字稿** | ✅ 上传 | docs_text/*_OCR.md | 讲义OCR后的文字稿（带_OCR后缀） |
| **转写文字稿** | ✅ 上传 | transcript.md | 视频转写后的文字稿（可读） |
| **验证报告** | ❌ 不上传 | 验证报告_*.md | 技术过程文档，仅用于质量验证 |
| **原始数据** | ❌ 不上传 | transcript.json | 转写原始JSON，非面向使用者 |
| **临时文件** | ❌ 不上传 | *.tmp, *.log | 临时文件和日志 |

### 3.2 原则

1. **面向使用者**：网盘内容的读者是学习者，不是开发者/维护者
2. **技术过程文档保留在本地**：验证报告、原始数据等只放在本地课程目录，不上传网盘
3. **上传前检查**：批量上传前，按上表筛选，排除技术过程文档
4. **定期清理**：定期检查网盘内容，删除误上传的技术过程文档

### 3.3 自动化

上传脚本（`scripts/batch_upload.sh` 和 `scripts/baidu_upload.py`）应自动过滤以下文件：
- `验证报告_*.md`
- `transcript.json`
- `*.tmp`, `*.log`

## 四、测试闭环检查原则

每次测试流程完成前，必须按检查清单确认所有步骤完成，避免遗漏最后一步（如做题验证）。

### 4.1 为什么需要闭环检查

- 测试流程通常有多个步骤，完成前面的步骤后容易注意力转移，遗漏最后一步
- 最后一步（如做题验证）往往是验证测试质量的关键，遗漏会导致测试不完整
- 没有检查清单时，"完成"的标准不明确，容易误以为测试已完成

### 4.2 闭环检查清单

每个测试流程必须包含以下检查项（根据具体测试调整）：

| 检查项 | 说明 |
|--------|------|
| **前置任务完成** | 视频下载/压缩/转写/OCR等前置任务全部完成 |
| **核心产出完成** | 知识库页面/文档/报告等核心产出物已生成 |
| **质量验证完成** | 视频可播放、文档内容完整、格式正确 |
| **反馈闭环完成** | 做题验证/用户反馈/错题补充等反馈环节完成 |
| **文档同步完成** | 任务状态、测试报告、知识库等文档已同步更新 |
| **临时文件清理** | 测试过程中产生的临时文件已清理 |

### 4.3 执行方式

1. **测试开始前**：在 TASK_STATUS.md 的"当前进行中"部分列出完整的测试流程步骤和检查清单
2. **每完成一步**：更新任务状态，标记为 ✅
3. **认为测试完成前**：按检查清单逐项确认，所有项都 ✅ 才能标记测试完成
4. **发现遗漏时**：立即补做遗漏的步骤，不跳过

### 4.4 示例

税法01完整流程测试的检查清单（见 TASK_STATUS.md）：
- ✅ 视频下载+压缩+验证+上传
- ✅ 讲义下载+OCR
- ✅ 视频转写
- ✅ 生成知识库页面（知识本身+考试指导）
- ✅ 父页面目录+子节点链接
- ✅ 互联网分享权限设置
- 🔄 做题验证知识库（完成作业+错题反馈）
- ⏳ 测试报告生成

## 五、状态查询协议触发机制

### 5.1 触发场景

当用户询问项目状态、任务、问题、维护工作等信息时，AI必须触发状态查询协议，而不是凭记忆或猜测回答。

**典型触发话术**（包括但不限于）：
- "还有什么要做的"、"当前进度"、"下一步是什么" → Q1 任务状态查询
- "有什么问题"、"有哪些bug"、"有什么异常" → Q2 问题/BUG查询
- "需要做什么维护"、"有什么待优化"、"定期检查什么" → Q3 维护工作查询
- "给项目做个体检"、"维护一下项目"、"检查目录结构/文档规范"、"文档健康度检查" → Q7 项目维护检查（执行型：实际扫描、分级、修复并出报告，见 PROJECT_STATUS_QUERY）
- "某某文档在哪里"、"怎么操作某某"、"流程是什么" → Q4 文档/操作查询
- "项目现在什么情况"、"总结一下"、"整体进度" → Q5 项目概览查询
- "为什么这样做"、"之前做了什么决定" → Q6 决策/历史查询
- "刷新Playwright token" → 自动化token刷新流程

### 5.2 执行流程

1. **识别意图**：根据模糊表达映射表，判断用户查询属于哪一类（Q1-Q6）
2. **读取权威文档**：根据意图，读取对应的权威文档（TASK_STATUS / ISSUES / PROJECT_MAINTENANCE / DOCUMENTATION_MAP / README / ADR）
3. **结构化响应**：按标准响应格式回答，不凭记忆或猜测
4. **意图不明确时**：主动给用户2-3个选项，让用户选择，而不是猜测

### 5.3 权威文档对应关系

| 查询意图 | 权威文档 | 说明 |
|----------|----------|------|
| Q1 任务状态 | `project-management/active/TASK_STATUS.md` | 唯一任务状态来源 |
| Q2 问题/BUG | `project-management/active/ISSUES.md` | 问题跟踪唯一来源 |
| Q3 维护工作 | `docs/project-management/standards/PROJECT_STRUCTURE_MAINTENANCE.md` + TASK_STATUS待优化项 | 维护规范和待优化项 |
| Q7 维护检查（执行型） | `PROJECT_STRUCTURE_MAINTENANCE.md` + `DOCUMENTATION_OPTIMIZATION.md`第12章 + `DIRECTORY_STRUCTURE.md` | 实际执行结构+文档健康度检查并出报告 |
| Q4 文档/操作 | `docs/DOCUMENTATION_MAP.md` + `docs/WORKFLOW.md` | 文档索引和工作流 |
| Q5 项目概览 | `README.md` + `TASK_STATUS.md` | 项目介绍和任务状态 |
| Q6 决策/历史 | `docs/project-management/decisions/ADR-*.md` | 架构决策记录 |

### 5.4 完整协议文档

详细的查询意图分类、模糊表达映射表、标准响应格式见：
`docs/project-management/standards/PROJECT_STATUS_QUERY.md`

常用查询话术速查表（27条）见：
- `README.md` 常用查询话术表格（精简版，7条最常用）
- `docs/project-management/standards/PROJECT_STATUS_QUERY.md` 第零节（完整版，27条）

## 六、批量重命名与结构整改流程（SOP）

> 适用：批量重命名、跨目录移动、命名/治理规范本身修订等 **L1 高扩散变更**（分级见 `AGENTS.md` 3.2）。这类变更必须"先方案、确认后执行"，禁止先改后报批。命名风格的具体规则以 `NAMING_CONVENTION.md` 第九章为**唯一事实源**，本章只定流程、不复述规则，避免同一规则多处写、互相矛盾。

### 6.1 七条总原则

1. **先方案后执行**：未拿到用户对"全量清单"的确认，不执行任何 `git mv` / 删除。
2. **全量一个不漏**：覆盖范围内所有文件都列出，无问题的也要列；范围与排除项（如 `data/`、隐藏目录、是否含中文文件）先与用户约定。
3. **三列起步、四列交付**：每个文件给"老名 / 新名 / 依据"，执行方案再加"影响面（被哪些文件引用）"。
4. **先改依据、再改文件**：规则本身有矛盾时先改 SSOT 规范并自洽复核，再据规则改名（第 2 步先于第 3 步）。
5. **判型看实质**：以正文是"强制标准"还是"操作教程"定文档类型，头部自标仅作声明，冲突时先修头部（见 NAMING 9.1.1）。
6. **git mv 保留历史 + 全量级联**：用 `git mv`；同步改相对链接、目录树、脚本自指注释、`.gitignore` glob 等一切引用点。
7. **本地改完待验收**：全部改完并回归通过后先不 push，交用户验收后再提交。

### 6.2 标准七步与每步交付物

| 步 | 动作 | 交付物（落盘到 verification-reports/） | 进入下一步的门 |
|---|---|---|---|
| 1 问题调研 | 按目录树逐文件检查，无问题也列；问题分类 | 《问题调研报告》 | 问题清单与范围经用户确认 |
| 2 修订依据规范 | 改 SSOT 规范、消除自相矛盾、自洽复核 | 依据文档优化记录 | 规范自身 0 矛盾 |
| 3 出整改方案 | 老名/新名/依据/影响面四列全量清单，文件名标"待确认" | 《全量文件清单_待确认》，套 `REFACTOR_PLAN_TEMPLATE.md` | —— |
| 4 用户确认 | 等用户逐行确认 / 纠错，更新清单至 0 待决 | 清单定稿 | **硬门：未确认不执行** |
| 5 执行 | `git mv` + 全部引用级联 | —— | 每个改名的引用点清零 |
| 6 回归验证 | 跑 `check_naming_consistency.py` + 6.3 回归单 | 回归结果 | 全部达标 |
| 7 记录收尾 | CHANGELOG、过程报告归档；验收后 commit/push | CHANGELOG 条目 | 用户验收 |

> 每一步都可能多轮迭代；上一步交付物是下一步输入，不跨步省略。

### 6.3 第 6 步回归核对单（必过）

- [ ] 旧名在"活文档"中 0 残留（历史报告 / ADR / CHANGELOG 中的轨迹性旧名保留）
- [ ] 相对链接 0 个真实断链（模板里的教学占位链接除外，且需逐一确认确为占位）
- [ ] 文档类型 ↔ 文件名风格 0 不自洽（脚本 `scripts/check_naming_consistency.py`）
- [ ] 目录树（DIRECTORY_STRUCTURE、各 README）与实际文件一致
- [ ] pre-commit 五项检查通过
- [ ] 汇总数字（总数 / 改名 / 移动 / 删除）由明细现算、前后一致

### 6.4 新建 / 删除持久文档前

按 `AGENTS.md` 3.4 门禁：先列职责、逐一指认现有权威源，已被承担则不新建；删除一份文档前，先确认其职责均有权威源承接，并清理全部活文档引用（历史报告中的轨迹保留）。

### 6.5 常见错误（本次整改教训）

- ❌ 把批量改名当"小问题"先执行后报批 → 必须走 L1 确认门。
- ❌ 只看头部"文档类型"自标就判风格，陷入循环论证 → 看正文实质。
- ❌ 改了文件名没级联引用 / 漏改目录树 → 第 5 步用影响面清单逐项销项。
- ❌ 同一规则在多份文档复述导致互相矛盾 → 只在 SSOT 写规则，其它文档引用不复述。
