# 项目维护规范

> **文档类型**：Governance（治理规范）
> **更新频率**：维护规则变更时
> **维护者**：AI自动维护
> **读者**：AI代理（项目维护时必须遵守）

本文档记录项目维护的详细规则，包括结构维护、文档组织、文档分解、文档分类、Docs as Code 理念和 AI 友好写作原则。

> 本文档是 README.md 中"项目维护规则"的详细展开，README 只保留核心摘要和链接。

---

## 一、结构维护原则

1. **GitHub 仓库只放代码和文档**：Skill 脚本、项目文档、工作流、报告模板、加密凭证。生成结果（视频、PDF、文字稿、音频）不放在项目目录，放本地 `~/Desktop/高顿/` 和百度网盘。
2. **脚本统一放 `scripts/`**：所有可执行脚本（Python、Shell）统一放在 `scripts/` 目录，不分散在各子目录。
3. **文档按专业领域分类**：`docs/project-management/`（项目管理）、`docs/development/`（开发文档），WORKFLOW.md 只保留总体流程和索引。
4. **任务文档不放根目录**：任务状态、测试计划、项目计划等统一放 `docs/project-management/`。
5. **定期清理**：测试文件、临时日志、残留目录及时清理，不堆积。

### 检查触发时机

- 开始新任务前：读取项目文档时检查结构
- 完成大任务后：检查是否产生新的散乱文件
- 发现结构问题时：主动梳理调整，不等待积累

## 二、文件归属原则

| 文件类型 | 放置位置 | 说明 |
|----------|----------|------|
| 通用规范/流程 | `docs/` 对应子目录 | 如 QUALITY_ASSURANCE.md、PROJECT_MAINTENANCE.md |
| 通用模板 | `reports/` 或 `docs/` | 如 REPORT_TEMPLATE.md、VERIFICATION_TEMPLATE.md |
| 具体课程产出物 | 对应课程目录下 | 如 video.mp4、knowledge.md、transcript.md |
| 具体课程验证报告 | 对应课程目录下 | 如 VERIFICATION_knowledge.md |
| 具体课程测试计划 | `docs/project-management/` | 测试计划是项目管理文档，不是课程产出物 |
| 具体任务报告 | `reports/` 或对应课程目录 | 根据报告性质决定 |

**原则**：针对具体课程/讲座的产出物，放在对应课程目录下；通用模板和规范放在 `docs/` 或 `reports/` 下。

## 三、文档组织原则（三层保障）

重要规则通过三层机制保障，避免"写在深文档里没人读"的问题：

| 层级 | 位置 | 内容 | 保障程度 |
|------|------|------|----------|
| 第一层 | **README.md 正文** | 核心规则、维护原则、存储分工 | 每次读 README 都能看到 |
| 第二层 | **docs/ 子文档** | 详细操作步骤、参数、常见问题 | 按需深入读取 |
| 第三层 | **自动化机制** | pre-commit hook、脚本检查 | 不依赖读不读文档，自动执行 |

**规则**：
- 核心规则必须写在 README 正文，不能只放子文档链接
- 详细内容放 `docs/` 对应子文档，README 放摘要和链接
- 可自动化的检查（大文件、敏感信息）必须用 pre-commit hook 强制执行
- 新增重要规则时，先问自己：这个规则放在哪一层？只放子文档够吗？

## 四、文档分解原则

当文档过大或内容跨领域时，必须分解为独立文档，避免单文档臃肿难维护。

### 触发分解的信号

- 文档超过 **500 行** 或阅读时间超过 10 分钟
- 内容覆盖 **2 个以上独立专业领域**（如 git 操作 + 视频压缩 + OCR）
- 某个子主题有独立的配置、参数、常见问题，可单独查阅
- 需要频繁更新某个子主题，但其他部分很少变动

### 分解方式

1. 按专业领域建目录：`docs/development/`、`docs/project-management/`
2. 目录下按主题分文档：`git-workflow.md`、`transcription.md`、`ocr.md`
3. 父文档（如 WORKFLOW.md）只保留**总体流程 + 索引链接**，不保留详细内容
4. 每个子文档独立完整，可单独阅读，不依赖父文档上下文

### 反例（不要这样做）

- ❌ 把所有内容都塞在 WORKFLOW.md 里，超过 1000 行
- ❌ 分解后父文档只放链接不放摘要，导致不点开链接不知道内容是什么
- ❌ 子文档引用父文档的上下文，单独阅读时看不懂

### 实例

WORKFLOW.md 原包含视频转写、OCR、Git 操作等详细内容，已分解为：
- `docs/development/workflow/git-workflow.md`（Git 工作流）
- `docs/development/tools/transcription.md`（音频转文字）
- `docs/development/tools/ocr.md`（OCR 文字提取）
- `docs/development/api/netdisk-setup.md`（百度网盘集成）
- WORKFLOW.md 只保留总体流程和索引链接

## 五、文档分类原则（Diátaxis 框架）

参考 Diátaxis 框架（Ubuntu、Python、Cloudflare、Microsoft 采用），按读者目的将文档分为四类，避免混合类型导致"什么都讲了但什么都不清楚"：

| 类型 | 读者目的 | 结构 | 本项目示例 |
|------|----------|------|------------|
| **教程 Tutorial** | 学习（跟着做） | 目标→前置条件→步骤→验证→常见问题 | 新手上手指南 |
| **操作指南 How-to** | 完成具体任务 | 问题→步骤→结果 | 如何下载视频、如何压缩、如何上传网盘 |
| **参考 Reference** | 查事实 | 参数列表、配置项、命令说明 | ffmpeg 参数、百度网盘 API、SSH 配置 |
| **解释 Explanation** | 理解概念 | 背景→原理→讨论→参考 | 为什么用 H.265、为什么 SSH 443 可直连 |

**规则**：
- 每个文档主要属于一种类型，不混合
- 操作指南和参考分开："怎么做"和"参数是什么"不要混在一篇
- 教程和操作指南分开：教程假设零基础，操作指南假设已有基础
- 写文档前先判断：读者读这篇文档是想学习、想完成任务、想查参数、还是想理解概念？

### 文档类型标注（强制）

**每个文档开头必须标注类型**，格式如下：

```markdown
# 文档标题

> **文档类型**：Task（操作指南）/ Concept（概念说明）/ Reference（参考资料）/ Governance（治理规范）/ Active（过程记录）/ Knowledge（知识内容）
> **更新频率**：每次流程变更时 / 每月定期 / 按需
> **维护者**：AI自动维护 / AI+用户审核 / 用户维护
> **读者**：AI代理 / 人类 / AI+人类
```

**本项目使用的文档类型**：

| 类型 | 说明 | 示例 |
|------|------|------|
| **Governance** | 治理规范，AI必须遵守的规则 | AGENTS.md, 项目维护规范, 质量保证规范 |
| **Task** | 操作指南，教你怎么做 | WORKFLOW.md, 视频处理指南, 做题流程与交互规范 |
| **Concept** | 概念说明，解释是什么 | README.md, 知识库组织结构说明 |
| **Reference** | 参考资料，查事实用 | DOCUMENTATION_MAP.md, 脚本说明, 命名规范 |
| **Active** | 过程记录，做了什么 | TASK_STATUS.md, 做题记录, 验证报告 |
| **Knowledge** | 知识内容，学什么用 | 知识拆解.md, 考试指导.md |

**已完成类型标注的核心文档**：AGENTS.md (Governance), README.md (Concept), WORKFLOW.md (Task), DOCUMENTATION_MAP.md (Reference)。其他文档在后续维护中逐步补充标注。

## 六、Docs as Code 理念

文档即代码，用管理代码的方式管理文档：

- **文档与代码同仓库**：文档放在项目仓库中，随代码一起版本控制
- **文档更新是"完成定义"的一部分**：改了脚本/流程，必须同步更新对应文档
- **文档腐化是最大敌人**：过时的文档比没有文档更危险（误导）
- **定期审查**：每次大任务后检查相关文档是否需要更新
- **问题驱动更新（强制）**：发现任何问题（文件位置不对、脚本有bug、流程有缺陷、数据不一致等）时，必须立即评估：
  1. 这个问题是否反映了文档缺失或过时？
  2. 是否需要更新现有文档（如 WORKFLOW.md、测试计划、SKILL）？
  3. 是否需要新增文档（如记录问题和解决方案）？
  4. 是否需要更新自动化检查（如 pre-commit hook）？
  - 评估后必须执行，不能只发现问题不更新文档
  - 示例：发现"转写结果位置不统一"→ 更新测试计划记录问题 → 更新转写脚本输出路径 → 更新 WORKFLOW.md 明确输出位置

## 七、文档定期梳理机制

文档梳理不是一次性工作，需要持续进行，避免文档重叠、冗余、组织不合理、表达不精练。

### 梳理目标

- **无重叠**：不同文档不重复描述同一内容，明确分工
- **无冗余**：删除过时、重复、无用的内容
- **无错误**：事实、链接、参数、命令、路径准确无误
- **无遗漏**：重要内容、完整流程、关键参数不缺失
- **组织合理**：文档按专业领域分类，目录结构清晰
- **表达精练**：删除教条化表述，保留核心信息，避免冗长

### 梳理触发时机

| 时机 | 说明 |
|------|------|
| **每次大任务后** | 完成一个完整流程（如下载+压缩+转写+知识库）后，检查相关文档是否需要梳理 |
| **每月定期** | 每月底进行一次全面文档梳理，统计文档数量、大小、重叠情况 |
| **发现问题时** | 发现文档重叠、冗余、组织不合理、表达不精练时，立即梳理 |
| **新增文档时** | 新增文档前，先检查是否已有类似文档，避免重复创建 |

### 梳理清单

每次梳理时，按以下清单检查：

| 检查项 | 检查方法 | 处理方式 |
|--------|----------|----------|
| **重叠检查** | 搜索相同关键词，看是否在多个文档中重复描述 | 明确分工，一个主题只在一个文档中详细描述，其他文档引用 |
| **冗余检查** | 检查是否有过时内容、重复段落、无用章节 | 删除过时内容，合并重复段落 |
| **错误检查** | 检查事实错误、链接失效、参数错误、命令错误、路径错误 | 修正错误，验证修正后的内容 |
| **遗漏检查** | 检查重要内容是否遗漏、流程是否完整、参数是否缺失、步骤是否跳步 | 补充遗漏内容，完善流程 |
| **脚本说明完整性** | 检查 scripts/ 下每个脚本是否在 scripts/README.md 中有说明（用途/用法/依赖） | 补充缺失的脚本说明，新增脚本时必须同步更新 |
| **路径引用正确性** | 检查文档中引用的脚本路径、文件路径、目录路径是否正确（如 transcription/ vs scripts/） | 修正错误路径，验证引用有效 |
| **脚本关系清晰性** | 检查脚本之间的调用关系是否说明清楚（如单文件+批量的分工） | 在 scripts/README.md 中补充脚本关系说明 |
| **组织合理性** | 检查文档分类是否合理，目录结构是否清晰 | 按专业领域重新分类，调整目录结构 |
| **表达精练性** | 检查是否有教条化表述、冗长解释、无用背景 | 精简表述，保留核心信息，删除无用背景 |
| **链接有效性** | 检查文档间的链接是否有效 | 修复失效链接，更新引用路径 |
| **大小合理性** | 检查单文档是否过大（>500行） | 按文档分解原则拆分 |

### 处理方式

| 问题类型 | 处理方式 |
|----------|----------|
| 内容重叠 | 合并为一个文档，或明确分工（一个详细，一个引用） |
| 内容冗余 | 删除重复、过时、无用的内容 |
| 内容错误 | 修正错误，验证修正后的内容（事实/链接/参数/命令/路径） |
| 内容遗漏 | 补充遗漏内容，完善流程（重要内容/完整流程/缺失参数/跳步步骤） |
| 脚本说明缺失 | 在 scripts/README.md 补充用途/用法/依赖/相关文档 |
| 路径引用错误 | 修正文档中的脚本/文件/目录路径引用，验证引用有效 |
| 脚本关系不清晰 | 在 scripts/README.md 补充脚本调用关系和分工说明 |
| 组织不合理 | 重新分类，调整目录结构 |
| 表达不精练 | 精简表述，删除教条化内容 |
| 文档过大 | 按文档分解原则拆分为多个子文档 |
| 文档缺失 | 新增文档，先检查是否已有类似文档 |

### 梳理记录

每次梳理后，在 Git commit message 中记录梳理内容，例如：
```
refactor: 文档梳理优化，减少重叠和冗余

1. 验证报告移到对应课程目录下
2. 新增 PROJECT_MAINTENANCE.md，抽离 README 中的项目维护详细规则
3. 精简 README 项目维护规则（从116行减到约30行）
4. 删除 README 中重复的存储分工章节
5. 精简 baidupan.md 为 Skill 快速参考
```

### 梳理统计

定期统计文档情况，跟踪文档质量趋势：

```bash
# 统计文档数量
find . -name "*.md" -not -path "*/.git/*" -not -path "*/venv/*" | wc -l

# 统计各目录文档数量
find . -name "*.md" -not -path "*/.git/*" -not -path "*/venv/*" | sed 's|/[^/]*$||' | sort | uniq -c | sort -rn

# 统计文档大小
find . -name "*.md" -not -path "*/.git/*" -not -path "*/venv/*" -exec wc -c {} \; | sort -rn | head -10
```

## 八、AI 友好写作原则

本项目文档主要供 AI（助手）读取和执行，写作时遵循：

1. **答案在前**：每节开头先给结论/操作，再讲原因。AI 不需要先读背景再找答案
2. **短段落**：2-3 句一段，避免大段文字。AI 提取信息时短段落更准确
3. **标题反映问题**：用"如何配置 SSH"而不是"SSH 配置"，用"为什么 push 慢"而不是"Push 问题"
4. **标题层级不跳级**：H1→H2→H3，不要从 H2 跳到 H4
5. **可执行的命令完整给出**：不要只说"运行脚本"，要给出完整命令和预期输出
6. **参数用表格**：配置项、参数、命令选项用表格，AI 更容易提取
7. **明确"不要做什么"**：反例和禁忌比正面说明更重要（如"不要把视频提交到 git"）

## 九、网盘上传内容筛选原则

百度网盘只上传**面向使用者**的内容，技术过程文档不上传。

### 上传分类

| 类别 | 上传？ | 示例 | 说明 |
|------|--------|------|------|
| **视频** | ✅ 上传 | video.mp4 | 课程视频 |
| **知识文档** | ✅ 上传 | knowledge.md, exam-guide.md | 知识本身和考试指导 |
| **讲义原件** | ✅ 上传 | docs/*.pdf | 原始讲义 |
| **讲义文字稿** | ✅ 上传 | docs/讲义文字稿.md | 讲义OCR后的文字稿 |
| **转写文字稿** | ✅ 上传 | transcript.md | 视频转写后的文字稿（可读） |
| **验证报告** | ❌ 不上传 | VERIFICATION_*.md | 技术过程文档，仅用于质量验证 |
| **原始数据** | ❌ 不上传 | transcript.json | 转写原始JSON，非面向使用者 |
| **临时文件** | ❌ 不上传 | *.tmp, *.log | 临时文件和日志 |

### 原则

1. **面向使用者**：网盘内容的读者是学习者，不是开发者/维护者
2. **技术过程文档保留在本地**：验证报告、原始数据等只放在本地课程目录，不上传网盘
3. **上传前检查**：批量上传前，按上表筛选，排除技术过程文档
4. **定期清理**：定期检查网盘内容，删除误上传的技术过程文档

### 自动化

上传脚本（`scripts/batch_upload.sh` 和 `scripts/baidu_upload.py`）应自动过滤以下文件：
- `VERIFICATION_*.md`
- `transcript.json`
- `*.tmp`, `*.log`

## 十、测试闭环检查原则

每次测试流程完成前，必须按检查清单确认所有步骤完成，避免遗漏最后一步（如做题验证）。

### 为什么需要闭环检查

- 测试流程通常有多个步骤，完成前面的步骤后容易注意力转移，遗漏最后一步
- 最后一步（如做题验证）往往是验证测试质量的关键，遗漏会导致测试不完整
- 没有检查清单时，"完成"的标准不明确，容易误以为测试已完成

### 闭环检查清单

每个测试流程必须包含以下检查项（根据具体测试调整）：

| 检查项 | 说明 |
|--------|------|
| **前置任务完成** | 视频下载/压缩/转写/OCR等前置任务全部完成 |
| **核心产出完成** | 知识库页面/文档/报告等核心产出物已生成 |
| **质量验证完成** | 视频可播放、文档内容完整、格式正确 |
| **反馈闭环完成** | 做题验证/用户反馈/错题补充等反馈环节完成 |
| **文档同步完成** | 任务状态、测试报告、知识库等文档已同步更新 |
| **临时文件清理** | 测试过程中产生的临时文件已清理 |

### 执行方式

1. **测试开始前**：在 TASK_STATUS.md 的"当前进行中"部分列出完整的测试流程步骤和检查清单
2. **每完成一步**：更新任务状态，标记为 ✅
3. **认为测试完成前**：按检查清单逐项确认，所有项都 ✅ 才能标记测试完成
4. **发现遗漏时**：立即补做遗漏的步骤，不跳过

## 十一、状态查询协议触发机制

### 11.1 触发场景

当用户询问项目状态、任务、问题、维护工作等信息时，AI必须触发状态查询协议，而不是凭记忆或猜测回答。

**典型触发话术**（包括但不限于）：
- "还有什么要做的"、"当前进度"、"下一步是什么" → Q1 任务状态查询
- "有什么问题"、"有哪些bug"、"有什么异常" → Q2 问题/BUG查询
- "需要做什么维护"、"有什么待优化"、"定期检查什么" → Q3 维护工作查询
- "某某文档在哪里"、"怎么操作某某"、"流程是什么" → Q4 文档/操作查询
- "项目现在什么情况"、"总结一下"、"整体进度" → Q5 项目概览查询
- "为什么这样做"、"之前做了什么决定" → Q6 决策/历史查询
- "刷新Playwright token" → 自动化token刷新流程

### 11.2 执行流程

1. **识别意图**：根据模糊表达映射表，判断用户查询属于哪一类（Q1-Q6）
2. **读取权威文档**：根据意图，读取对应的权威文档（TASK_STATUS / ISSUES / PROJECT_MAINTENANCE / DOCUMENTATION_MAP / README / ADR）
3. **结构化响应**：按标准响应格式回答，不凭记忆或猜测
4. **意图不明确时**：主动给用户2-3个选项，让用户选择，而不是猜测

### 11.3 权威文档对应关系

| 查询意图 | 权威文档 | 说明 |
|----------|----------|------|
| Q1 任务状态 | `docs/project-management/active/TASK_STATUS.md` | 唯一任务状态来源 |
| Q2 问题/BUG | `docs/project-management/active/ISSUES.md` | 问题跟踪唯一来源 |
| Q3 维护工作 | `docs/project-management/standards/PROJECT_MAINTENANCE.md` + TASK_STATUS待优化项 | 维护规范和待优化项 |
| Q4 文档/操作 | `docs/DOCUMENTATION_MAP.md` + `docs/WORKFLOW.md` | 文档索引和工作流 |
| Q5 项目概览 | `README.md` + `TASK_STATUS.md` | 项目介绍和任务状态 |
| Q6 决策/历史 | `docs/project-management/decisions/ADR-*.md` | 架构决策记录 |
